# The road to 1.0

Written 18 November 2026 at version 0.8.33, while PlanView Dash waits in the queue for the Marketplace catalog and G1 (launch) is under way. The tasks themselves, with **Done when**, are in [plan.md](plan.md) under *1.0 release: stable* (V1–V7). This page is the reasoning behind them and the owner's decisions (all five recommendations accepted on 18 November 2026).

## In short

Feature-wise, 1.0 is already here. Every task in the 1.0 milestone is done except G1, and the owner's three priorities (lights, temperature and energy flow) work on the picture today. What 1.0 still lacks is not a feature but a **promise**: that a dashboard you set up today keeps working after every update in 1.x, and that the three core features behave well on homes other than the one they were built on.

So the path is short, and it adds no new features:

1. **0.8.34 – 0.8.x: hardening** (V1–V5), one patch release each, alongside G1.
2. **0.9.0: the 1.0 beta.** The config format is frozen and versioned, the public names are final, the core features are hardened. Announced as a beta in the launch posts, so the first outside users know feedback lands before 1.0.
3. **0.9.x: fixes only**, from what beta users report. No new features.
4. **1.0.0** once a 0.9.x release has stood for **two weeks with no fix needed** and the release checklist (V7) is ticked. The same code as the last 0.9.x, with the version changed.

Everything in 1.1 and later (people in rooms, solar forecast, summer house mode …) waits until after 1.0. Adding features now would reset the two weeks of quiet that 1.0 is supposed to prove.

## What 1.0 promises

These lines go into the README and `docs/configuration.md` with 1.0 (task V4):

- **Your dashboard keeps working.** A `site.json` saved by any 1.x version opens in every later 1.x version, and is upgraded by itself when the format grows. Nothing you set up has to be redone.
- **Names stay.** The domain `planview_dash`, the card `custom:planview-dash-card` and its options, the actions `planview_dash.goodnight` (and their fields), the `planview_dash.goodnight_<site>` state and the panel addresses do not change in 1.x.
- **Breaking changes wait for 2.0**, are announced one minor release ahead in the changelog and in Home Assistant's repairs, and come with an automatic migration where one is possible.
- **Supported Home Assistant versions** are the ones CI tests: the newest, and the oldest named in `hacs.json`. Raising the oldest is announced in the changelog.
- **Version numbers** follow SemVer from 1.0: 1.0.1 fixes, 1.1.0 features, 2.0.0 breaking changes. (Before 1.0 the owner's rule stays: a patch per task.)

## Why each task is there

### V1: A versioned, frozen config format (the main reason for 1.0)

Today `site.json` has no version field, and no step upgrades an older file: there is only the check before a save (`validate_site` in `views.py`). That has worked because there is one home and every change so far added optional keys. After 1.0 a format change without a version field means guessing what a file meant.

V1 adds `"format": 1` to `site.json` (new files get it, files without it count as 1), one place where migrations run (`site.js` on load, and the same steps in Python for the check), and a review of the format before it is frozen: names that are awkward now are cheap to fix and expensive later. `mock` (test data only) is kept out of the documented user format. A file with a higher `format` than the running version knows is shown read-only with a clear message instead of being saved over.

### V2: Final public names, and what happens to the self-updater

The rename to PlanView Dash in 0.8.33 was the big one, and it is good it happened before 1.0. What is left is a check of everything a user can type into Home Assistant: action names and fields, card options, the goodnight state, `configuration.yaml` keys. Anything that would be renamed must be renamed now.

The **`planview_dash.update` action** (`updater.py`, and the **Uppdatera dashboarden** button in placement mode) downloads code from GitHub and replaces the integration. It predates the Marketplace, which now offers every update. It is the only part of the integration that calls an outside service, its messages are hard-coded in Swedish and English (not in the translations), and it is a second update path that can disagree with what the Marketplace thinks is installed. The owner decided to remove it before 0.9.0.

The migration from SmartHomeDash (`migrate.py`) is cheap to keep. It stays through 1.x and is removed in 2.0 (decided).

### V3: The core features on any home: lights, temperature and energy flow

These are what the owner cares about most, and they were built against one set of devices. Gaps found while writing this plan:

- **No test covers a device that is `unavailable` or `unknown`** (no browser test mentions either state). A lamp, a thermometer or an energy sensor that drops out should show as unavailable, not as off, 0 °C or 0 kW, and should not break the energy sentence or the flow lines.
- **A failed action is silent.** Tapping a lamp, all on/off, a scene, the thermostat's plus and minus, presets and blinds call Home Assistant without catching an error (`panel.js`, `cards.js`, `overview.js`, `lights.js`). When a light is offline or Home Assistant refuses, nothing tells the person at the wall; the promise just fails in the console. One small shared message ("Couldn't turn on Kitchen ceiling") fixes all of them.
- **Power units:** `kw()` in `entities.js` knows `W` and `kW`; anything else (`MW`, an empty unit) is read as watts. It should follow Home Assistant's power units and say so when a unit is unknown.
- **Sign conventions** for grid, battery and charger power differ between inverters and integrations. The setup guide has a direction check; V3 adds tests for both conventions on every flow (grid buying and selling, battery charging and giving, solar at night reading slightly negative) so the picture and the sentence agree.
- **Temperature:** °F homes, a room whose thermostat reports no current temperature, and a thermostat without presets or HVAC modes.

### V4: Docs for people who are not the owner

The docs are thorough but written as the project grew. Before 1.0: the promise above in the README; a short **Troubleshooting** page (nothing shows, a lamp does not glow, the energy flow points the wrong way, the card says it cannot find the site, how to send diagnostics); an **Upgrading** section that explains the Marketplace path and what a restart is needed for; and a pass over `docs/setup.md` following it from a clean install, fixing what is out of date.

### V5: Small cleanups that are easier before the freeze

- Make **Home Assistant (newest, oldest)** required checks on main (the owner's own to-do).
- Raise the newest Home Assistant in `tests/ha/requirements.txt` to 2026.11, the version the Marketplace launched in.
- Keep the oldest supported Home Assistant at 2025.6 (decided), and say so in the README.
- A security pass over everything that writes (save, pictures, import, restore) against `SECURITY.md`, as a last look before a promise is made.

### V6: The 0.9.0 beta release

Ships V1–V5 together as 0.9.0, the first minor release since 0.8.0. The launch posts from G1 say "beta, 1.0 coming" so early users know their reports count. A `bug` label and a short issue triage routine: every report answered within a few days during the beta.

### V7: The 1.0 release checklist

Done on real hardware by the owner, since CI cannot:

- The wall tablet runs the release for a week: idle, night dimming, motion wake, light mode, the **Aa** text size (also on the owner's to-do list).
- An iPad (Safari) and a phone: overview, a floor plan, a room, switching a lamp, pinch zoom.
- The card in a **sections** view of a Home Assistant dashboard (also on the to-do list).
- A clean install from the Marketplace on a Home Assistant without PlanView Dash: quick start to a working picture, following only `docs/setup.md`.
- An upgrade from the previous release with a real `site.json`: nothing lost.
- No open issue labelled `bug` that affects lights, temperature or energy flow.
- Two weeks since the last 0.9.x fix.

## What is deliberately not before 1.0

- **New features from 1.1–1.3.** Solar forecast (E1) and climate overlays (H6) are small and tempting, but they are features, and the beta is meant to settle what exists. They are the first things after 1.0.
- **A separate release-candidate tag.** The Marketplace only shows pre-releases to people who turned them on, and very few will. The last 0.9.x is the candidate; 1.0.0 is the same code.
- **Performance and accessibility work.** Both have measured budgets and tests (Q2, A1) that pass with room to spare. They stay as checks, not tasks.

## Decisions (owner, 18 November 2026)

The owner said yes to all five recommendations:

1. **The path:** hardening in 0.8.x → 0.9.0 beta → two quiet weeks → 1.0.0, with no new features until then.
2. **`planview_dash.update` and the update button are removed** before 0.9.0 (in V2); updates come from the Marketplace.
3. **The move-over from SmartHomeDash stays** through 1.x and is removed in 2.0.
4. **The oldest supported Home Assistant stays 2025.6**, as long as CI passes on it.
5. **The beta lasts two weeks without a fix** before 1.0 (shorter if no outside users show up).
